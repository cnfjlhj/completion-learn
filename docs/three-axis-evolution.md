# completion-learn：为什么任务完成以后，第一件事不是先改工具

很多人把“任务完成”当成结束点。

但对高频使用 AI 工具的人来说，任务真正完成的时刻，往往也是最容易浪费掉的时刻。因为这时有真实上下文、有真实代价、有真实判断偏差，也有真实的成功动作。你完全可以把这些东西沉淀成下一轮的优势；也完全可能在“总之做完了”的松弛感里，把它们全部丢掉。

`completion-learn` 的核心想法很简单：

> 完成不是终点，而是学习链路的入口。

但这个入口如果设计得不好，很快就会退化成两种没什么价值的东西：

1. 变成一份好看但无用的 recap
2. 变成一份工具狂热清单，只剩 prompt、脚本和自动化，没有人的成长

这就是 `completion-learn` 为什么要强行把默认顺序固定成：

1. `self`
2. `collaboration`
3. `tool`

## 一、为什么先是 Self

很多人在 AI 时代遇到的真正问题，不是工具不够强，而是自己的注意力已经被工具工作流吞掉了。

表面上看，你知道更多命令、更多 prompt、更多 skill；但如果你越来越少停下来问这些问题：

- 我到底在解决什么瓶颈？
- 我是不是把判断外包掉了？
- 这次我真正该练的是什么？
- 哪个时刻，如果我更早 noticing 到自己，就能少走很多弯路？

那工具越多，反而越容易被工具带着跑。

所以 `completion-learn` 把第一轴固定成 `self`，不是因为“个人成长”听起来更高级，而是因为如果第一轴不先把人的注意力、判断和 ownership 稳住，后面的 collaboration 和 tool discussion 很容易变成噪声。

默认 self 轴只要求四个很具体的输出：

- `Keep`
- `Stop`
- `Practice next`
- `Durable rule`

这是故意的。因为真正能改变下一轮行为的，不是抽象感悟，而是这四个动作。

## 二、为什么第二轴是 Collaboration

第二轴不是“团队协作鸡汤”，而是更机械的问题：

- 下次什么沟通模式应该成为默认？
- 什么澄清应该更早发生？
- 什么可见性最刚好，不会过载也不会失控？
- ownership 应该怎么切，人应该保留什么，工具应该代做什么？

很多任务之所以痛苦，不是因为人和工具单独都不行，而是因为两者之间的 operating loop 不稳定：

- done 的定义不一样
- 更新频率要么太高要么太低
- 工具过度自主，用户失去全局
- 用户过度细控，工具无法连续推进

`completion-learn` 把 collaboration 单独拉成一轴，是因为这里的收益非常高。一次任务里找出的更好协作模式，往往比某一个 prompt 的优化更耐用。

## 三、为什么 Tool 要放到最后

不是因为 tool 不重要，而是因为它太容易抢走注意力。

只要一做复盘，大家都很容易立刻跳到：

- 要不要再写个脚本？
- 要不要再加个命令？
- 要不要再拆一个 skill？
- 要不要把这个做成自动化？

这些问题本身没错，但它们太诱人了。它们给人一种“已经在进化系统”的感觉，可如果前两轴没有做好，最后只会得到一个越来越复杂的工具栈，以及一个越来越少真正自我观察的人。

所以 `completion-learn` 在第三轴里做两件事，而且都要求保持克制：

1. `skill sedimentation`
2. `existing skill optimize`

也就是说，tool 轴不是只问“要不要新建 skill”，而是同时问：

- 这段流程到底值不值得沉淀？
- 如果值得，应该是扩展旧 skill、补一个互补 skill，还是只是把现有 skill 优化好？

## 四、为什么要“先诊断，再路由”

用户之前问过一个很好的问题：

> 为什么不能让这个 skill 直接去调用创造 skill 的 skill，或者优化 skill 的 skill？

答案不是“绝对不能”，而是“不能把诊断和执行混成一个默认动作”。

原因很简单：

- 很多 task 的 tool lesson 其实还不稳定
- 很多问题不是缺 skill，而是已有 skill 太弱
- 很多时候最好的动作是 recommendation only，而不是立刻编辑技能文件

所以更合理的结构是：

1. `completion-learn` 先诊断
2. 如果判断是“边界对，但 skill 弱”，路由到 `skill-optimizer`
3. 如果判断是“边界应扩，或者应该补第二个 skill”，路由到 `skill-creator`
4. 如果证据不足，就停在 recommendation

这能避免一种很常见的坏结果：因为一轮任务刚结束，情绪和上下文都很饱满，于是把偶然问题当成稳定模式，过早写进工具系统里。

## 五、一个更适合长期使用的 learn loop

如果你长期和 AI 工具一起工作，可以把默认 learn loop 理解成下面这个顺序：

```text
task done
  -> self: 我自己该怎么更稳、更清楚、更强
  -> collaboration: 我跟工具的默认协作方式该怎么更顺
  -> tool: 哪些流程值得沉淀，哪些 skill 该优化
```

这个顺序的关键不是“全面”，而是“防偏”。

它防止复盘一上来就滑进工具崇拜，也防止你把注意力全部投到系统外壳上，却忽略了真正需要升级的是自己的观察力和判断节奏。

## 六、什么时候不该用它

`completion-learn` 故意不是一个“随时都能开”的 skill。

不要在这些时候用：

- 任务其实还没做完
- 你只是想要一个中途 checkpoint
- 你真正需要的是继续 debug / 继续实现 / 继续写，而不是复盘
- 你只是想要情绪安慰式总结

它只适合一个时刻：任务已经足够完成，可以诚实面对 outcome、mistake 和 verifier 的时刻。

## 七、公开这个 skill 的原因

之所以把它单独拆成一个仓库，是因为这条链路值得被看见：

- completion debrief 不该只是“收尾话术”
- self-improvement 不该在 AI 工作流里被压成附属品
- collaboration pattern 应该被系统化
- tool evolution 应该同时包含 skill 沉淀和 skill 自进化，而不是只会盲目加新东西

如果你也在高频使用 AI 工具，而且开始意识到“我需要的不只是更强的工具，而是更强的自己，以及更清楚的人机工作方式”，那这条 skill lane 可能对你有用。

回到最开始的那句话：

> 完成不是终点，而是学习链路的入口。

真正的问题不是“这次做完了没有”，而是“这次做完之后，你自己有没有真的变强一点”。
