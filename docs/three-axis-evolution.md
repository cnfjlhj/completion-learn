# 为什么任务做完以后，第一件事不是改工具

> 完成不是终点，而是沉淀链路的入口。

对高频使用 AI 工具的人来说，任务完成的时刻是最容易浪费的时刻。尤其是一段很长的人机对话刚结束时，上下文还在、输入过程还清楚、情绪和判断偏差也还看得见。这个时候，你要么把它们沉淀下来，要么它们很快就什么都不剩。

问题是，大多数复盘会退化成两种无价值的东西：

1. 一份好看但无用的 recap
2. 一份只剩 prompt、脚本和自动化的工具清单

`completion-learn` 的做法，是把“任务结束后留下些什么”拆成固定三层：**Self → Collaboration → Tool**。

---

## Self：为什么第一轴是人

很多人在 AI 时代遇到的真正问题不是工具不够强，而是自己的注意力、表达方式、情绪处理和判断节奏，已经被工具工作流吞掉了。

表面上看，你知道更多命令、更多 prompt、更多 skill。但如果你越来越少停下来问——

- 我这次是怎么把需求说清楚的，还是一直在把混乱继续放大？
- 我有没有在关键时刻被情绪带着跑？
- 我是不是把本该由自己承担的判断外包掉了？
- 这次从人的输入过程里，到底有什么值得留下来？

——那工具越多，反而越容易被工具带着跑。

所以第一轴固定是 Self。不是因为“个人成长”听起来更高级，而是因为如果不先看人这一层最后能沉淀什么，后面的讨论很容易直接滑到工具崇拜。

Self 轴看的不是结果，而是人的输入过程。它要沉淀的是：哪些觉察该保留，哪些表达方式该停止，哪些情绪模式该识别，哪些判断习惯值得继续练。

Self 轴只要求四个输出：**Keep · Stop · Practice next · Durable rule**。故意的。因为真正能留下来的，不是抽象感悟，而是这四个动作。

## Collaboration：为什么第二轴是协作

第二轴不是团队鸡汤，而是一个很机械的问题：这次你和 AI 之间的 operating loop，最后能沉淀下什么默认模式。

- 下次什么沟通模式应该成为默认？
- 什么澄清应该更早发生？
- 可见性多少刚好——不过载也不失控？
- Ownership 怎么切——人保留什么，工具代做什么？

很多任务之所以痛苦，不是因为人或工具单独不行，而是两者之间的协作模式不稳定：done 的定义不一样、更新频率不匹配、工具过度自主或用户过度细控。

一次任务里找出的更好协作模式，往往比某个 prompt 的优化更耐用，因为它是真正能在下次继续留下来的东西。

## Tool：为什么放到最后

不是因为工具不重要，而是因为它太容易抢走注意力，也最容易让人误以为“留下来的东西”只能是脚本、命令和自动化。

一做复盘，大家很自然地想：要不要再写个脚本？要不要再加个命令？要不要做成自动化？这些问题本身没错，但如果前两轴没有做好，最后只会得到一个越来越复杂的工具栈和一个越来越少自我观察的人。

所以 Tool 轴做两件事，而且都要求克制：

1. **Skill sedimentation** — 这段流程值不值得沉淀？
2. **Existing skill optimization** — 如果值得，是新建还是优化已有的？

这里不只是看“要不要新建一个东西”，也看 AI 自己在这轮任务里暴露了什么不足，哪些真的值得进入系统，哪些只是一次性的波动。

诊断先行。如果证据不够，就停在建议，不强行写进系统。

## 完成，不等于能力已经留下

这也是 `completion-learn` 最近补强的一点。

很多任务做完以后，最容易犯的错不是“没复盘”，而是**把完成错当成内化**。尤其当 AI 在场时，一次做成，可能只是因为：

- 这次主要是工具在搭脚手架
- 你已经抓住了一部分判断，但还需要辅助
- 你真的长出了一种可迁移的能力

这三种情况，结果看起来都可能是“任务完成了”，但它们对下一步该怎么练，完全不是一回事。

所以现在更稳的做法是：

```text
task done
  → (internal) capability residue judgment
  → self
  → collaboration
  → tool
```

其中那个内部判断，默认只服务两个目的：

1. 不把“一次做成了”误判成“已经学会了”
2. 让 `Next deliberate practice` 变成一个更像验收的动作

它默认不会长成第四轴。因为如果把它直接外显成新的结构层，很多复盘会立刻从“帮你沉淀”滑到“再讲一套理论”。这个 skill 不需要更响亮，它需要更诚实。

### 那么练习应该怎么变

如果一次结果更像：

- `mostly assisted performance`
  那下次练习就应该只拿出一个最小步骤，先让人独立做，再让工具补
- `partial internalization`
  那练习就应该沿着同一个瓶颈，先人后机，检查关键判断是不是还站得住
- `durable capability gain`
  那就不要机械复做原题，而应该迁移到相邻任务，看能力是不是能转移

这件事看起来像小改动，实际上非常关键。因为真正决定一个 learn skill 是否有用的，不是它会不会“讲得更好”，而是它能不能把下一次练习设计得更像检验，而不是鼓励。

## 先诊断，再路由

`completion-learn` 不直接假设"应该新建 skill"。它先诊断，再根据结果路由：

- 边界正确但 skill 太弱 → `skill-optimizer`
- 边界该扩或应补第二个互补 skill → `skill-creator`
- 证据不足 → 停在 recommendation

这能避免一种常见的坏结果：因为一轮任务刚结束、情绪和上下文都很饱满，把偶然问题当成稳定模式过早固化到工具系统里。

## 长期沉淀 loop

如果你长期和 AI 工具一起工作，把默认沉淀链路理解成：

```
task done
  → (internal) residue judgment:  这次更像辅助完成、部分内化，还是持久增长
  → self:                        从人的输入过程里，留下些什么
  → collaboration:               从人机协作里，留下些什么默认模式
  → tool:                        从工具层里，留下些什么系统改进
```

这个顺序的关键不是“全面”，而是**防偏**。它防止复盘一上来就滑进工具崇拜，也防止你把“一次完成”直接错认成“能力已经稳固”，却忽略了真正需要沉淀的是人的输入方式、协作模式和系统边界。

## 什么时候不该用

`completion-learn` 是 completion-only 的。不要在这些时候用：

- 任务还没做完
- 你只需要中途 checkpoint
- 你真正需要的是继续实现或 debug
- 你只是想要情绪安慰式总结

它只适合一个时刻：**任务已经足够完成，可以诚实面对结果、失误和判断的时刻。**

---

真正的问题不是“这次做完了没有”，而是这轮结束以后，你到底留下了什么。
