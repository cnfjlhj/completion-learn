# 为什么任务做完以后，第一件事不是改工具

> 完成不是终点，而是学习链路的入口。

对高频使用 AI 工具的人来说，任务完成的时刻是最容易浪费的时刻。上下文还在、代价还清楚、判断偏差还可见——你完全可以把它们变成下一轮的优势，也完全可以在"总之做完了"的松弛感里全部丢掉。

问题是，大多数复盘会退化成两种无价值的东西：

1. 一份好看但无用的 recap
2. 一份只剩 prompt、脚本和自动化的工具清单

`completion-learn` 的做法是把默认顺序强制固定：**Self → Collaboration → Tool**。

---

## Self：为什么第一轴是人

很多人在 AI 时代遇到的真正问题不是工具不够强，而是自己的注意力已经被工具工作流吞掉了。

表面上看，你知道更多命令、更多 prompt、更多 skill。但如果你越来越少停下来问——

- 我到底在解决什么瓶颈？
- 我是不是把判断外包掉了？
- 这次我真正该练的是什么？
- 哪个时刻如果我更早注意到，就能少走很多弯路？

——那工具越多，反而越容易被工具带着跑。

所以第一轴固定是 Self。不是因为"个人成长"听起来更高级，而是因为如果不先把人的注意力和判断稳住，后面的讨论全是噪声。

Self 轴只要求四个输出：**Keep · Stop · Practice next · Durable rule**。故意的。因为真正能改变下一轮行为的不是抽象感悟，而是这四个动作。

## Collaboration：为什么第二轴是协作

第二轴不是团队鸡汤，而是一个很机械的问题：人和工具之间的 operating loop 稳不稳定。

- 下次什么沟通模式应该成为默认？
- 什么澄清应该更早发生？
- 可见性多少刚好——不过载也不失控？
- Ownership 怎么切——人保留什么，工具代做什么？

很多任务之所以痛苦，不是因为人或工具单独不行，而是两者之间的协作模式不稳定：done 的定义不一样、更新频率不匹配、工具过度自主或用户过度细控。

一次任务里找出的更好协作模式，往往比某个 prompt 的优化更耐用。

## Tool：为什么放到最后

不是因为工具不重要，而是因为它太容易抢走注意力。

一做复盘，大家很自然地想：要不要再写个脚本？要不要再加个命令？要不要做成自动化？这些问题本身没错，但如果前两轴没有做好，最后只会得到一个越来越复杂的工具栈和一个越来越少自我观察的人。

所以 Tool 轴做两件事，而且都要求克制：

1. **Skill sedimentation** — 这段流程值不值得沉淀？
2. **Existing skill optimization** — 如果值得，是新建还是优化已有的？

诊断先行。如果证据不够，就停在建议，不强行写进系统。

---

## 先诊断，再路由

`completion-learn` 不直接假设"应该新建 skill"。它先诊断，再根据结果路由：

- 边界正确但 skill 太弱 → `skill-optimizer`
- 边界该扩或应补第二个互补 skill → `skill-creator`
- 证据不足 → 停在 recommendation

这能避免一种常见的坏结果：因为一轮任务刚结束、情绪和上下文都很饱满，把偶然问题当成稳定模式过早固化到工具系统里。

## 长期 learn loop

如果你长期和 AI 工具一起工作，把默认学习链路理解成：

```
task done
  → self:          我自己该怎么更稳、更清楚、更强
  → collaboration:  我跟工具的默认协作方式该怎么更顺
  → tool:           哪些流程值得沉淀，哪些 skill 该优化
```

这个顺序的关键不是"全面"，而是**防偏**。它防止复盘一上来就滑进工具崇拜，也防止你把注意力全部投到系统外壳上，却忽略了真正需要升级的是自己的观察力和判断节奏。

## 什么时候不该用

`completion-learn` 是 completion-only 的。不要在这些时候用：

- 任务还没做完
- 你只需要中途 checkpoint
- 你真正需要的是继续实现或 debug
- 你只是想要情绪安慰式总结

它只适合一个时刻：**任务已经足够完成，可以诚实面对结果、失误和判断的时刻。**

---

真正的问题不是"这次做完了没有"，而是做完之后，你自己有没有真的变强一点。
